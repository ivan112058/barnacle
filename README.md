# Barnacle

A semantic-first Neubrutalism UI library in pure CSS. Zero runtime dependencies, no shadow
DOM, no class-name API: you write the HTML element that already means what you mean and
Barnacle styles it.

> **Status: v1 feature-complete.** All twenty components, the base and theme layers, the
> documentation site, the bilingual edition and the GitHub Pages workflow are in place, and
> `static/` carries the built artifacts. The one thing still outstanding is the deployment
> itself: GitHub Pages has not been enabled for this repository yet, so
> <https://ivan112058.github.io/barnacle/> is not published. See
> [Going live](#going-live) for the exact steps and for the command that proves the site is up.

## Repository layout

```
seite.toml        seite configuration — base_url points at the Pages sub-path /barnacle/
content/          docs content: Markdown + YAML frontmatter
  pages/          /, /usage, /customizing
  components/     /components/ index + one page per component
templates/        Tera templates (seite resolves collection indexes as <collection>-index.html)
static/           committed build output + the docs site's own style.css
  barnacle.css    src/css/*.css concatenated, in the layer order of ADR-0006
  barnacle.min.css
  barnacle.js     src/js/index.js bundled as an IIFE
  barnacle.min.js
  style.css       docs site styling only — never mixed into the library
  site.js         docs site behaviour only: fences → Preview/Code pairs, theme switch
public/           copied to the root of dist/ (favicon, .well-known, CNAME, …)
src/              library sources (css/ and js/) — not part of the published site
scripts/          build.mjs, verify*.mjs (one per ticket) and verify-release.mjs,
                  the v1 release gate
docs/             ADRs and agent docs
dist/             generated by seite, gitignored
```

The published artifacts live in `static/`, not `dist/`: seite copies `static/` verbatim into
`dist/static/`, so one committed file is simultaneously the docs site's asset, the artifact
published with the repository, and the file jsDelivr can serve from the `main` branch.

## Library build

```powershell
npm install
npm run build     # src/ → static/barnacle{,.min}.{css,js}
npm run verify    # 21 build-chain checks (ticket 01)
```

`npm run build` fails loudly rather than emitting broken CSS: a file listed in
`scripts/build.mjs` that is missing on disk, or whose `@layer` placement breaks the
ADR-0006 contract, aborts the build with the offending file named.

## Documentation site

`seite` is **not on `PATH`** on this machine. Always call it by its absolute path:

```powershell
# local preview with live reload — http://127.0.0.1:4377
& "D:\sdk\seite\seite.exe" serve --port 4377

# one-off build into dist/
& "D:\sdk\seite\seite.exe" build

# link/asset validation; --strict turns warnings into a non-zero exit
& "D:\sdk\seite\seite.exe" check --strict
```

`seite serve` prints on stderr and serves from the origin root, so the preview URL is
`http://127.0.0.1:4377/` — **not** `/barnacle/`. Templates therefore reference every asset
through `{{ site.base_url }}`, which is the production sub-path when built and the dev
origin when served.

### Verifying the site

```powershell
node scripts/verify-site.mjs
```

This runs the checks ticket 02 promises: `seite build` and `seite check --strict` both clean,
the four published artifacts byte-identical between `static/` and `dist/static/`, every page
asset sub-path safe and present in `dist/`, every internal link resolving, the repository's
`AGENTS.md` untouched by the seite scaffold, `seite init`'s file list re-measured, and the
preview server actually serving `/` and `/components/`.

`node scripts/verify-site.mjs --minify-experiment` additionally builds with `minify = false`
and `minify = true` and prints the byte comparison. It is why `seite.toml` keeps
`minify = false`: with `true`, seite re-compresses the already-minified CSS and drops the
trailing newline from the JS, so `dist/static/` would no longer match the committed
artifacts.

### Verifying the sub-path deploy

```powershell
npm run verify:deploy
```

`seite serve` cannot reproduce the deployed layout — it always serves from the origin root —
so this script serves `dist/` itself under `/barnacle/`, the mount GitHub Pages uses for a
project site, and then requests every `href`/`src` on every built page. It fails on any
reference that leaves the `/barnacle` root, any non-200 (the four artifacts, `style.css` and
the favicon included) and any served file whose bytes differ from the committed one. It also
asserts the contents and step order of `.github/workflows/deploy.yml`. `--no-serve` and
`--no-build` skip the two halves.

### Verifying the release

```powershell
npm run verify:release            # offline: everything provable without the site being published
npm run verify:release -- --live  # the same gate, with the HTTP half pointed at the real deployment
```

`verify:release` (`scripts/verify-release.mjs`) is the v1 acceptance gate (ticket 24). Offline it
rebuilds `static/` and `dist/`, crawls the whole site from `/barnacle/` in both languages (BFS
over `<a href>`, no `file://`, no hand-written list of URLs), requests every asset, checks that
the crawl reaches every page seite published, that every bilingual page switches to its own
counterpart with matching `hreflang`, that dark mode holds on every page in real Chrome, that the
per-file consumption recipe below computes the same styles as the whole artifact, that the
README's CDN and raw URLs point at files that exist, and that the generated Chinese pages match
their English masters. `--no-build` reuses the existing `dist/`, `--no-browser` skips the Chrome
pass.

`--live` (or `BN_LIVE=1`) runs the same gate with the HTTP half pointed at
`https://ivan112058.github.io/barnacle/` and at the jsDelivr / raw mirrors of `main`: the same
crawl, the same asset list, dark mode against the deployed pages, and a byte-for-byte
comparison of all six published `static/` files. Until Pages is enabled it fails with
`GET https://ivan112058.github.io/barnacle/ → 404` and says so, which is the honest result —
a green offline run proves the site *would* work, only `--live` proves it does.

### Verifying the demo rendering layer

```powershell
node scripts/verify-demo.mjs
```

Ticket 04's checks: a component page's Markdown fences become Preview / Code pairs, the code
panel shows the fence source escaped, the Preview/Code tabs are keyboard operable, component
pages render exactly one H2 (the one the template supplies), and the header theme switch sets
`data-theme` on `<html>` and survives a reload. Authoring stays plain Markdown — a fence that
does not start with `<` stays a plain code block.

The last five checks drive real Chrome over the built site on `/barnacle/`. They need
`playwright-core`, which **is** a devDependency (ticket 08 pinned it to 1.64.1), so `npm ci`
installs it; they then drive the Chrome installed on the machine (`channel: 'chrome'`) and
download no browser of their own:

```powershell
npm ci
node scripts/verify-demo.mjs          # or: npm run verify:demo -- --no-browser
```

Without the module — or without a system Chrome — the browser checks report `SKIP` and the static
checks still gate the exit code. `npm run verify:release` follows the same rule.

## Deployment

`.github/workflows/deploy.yml` is seite's own GitHub Pages workflow (`upload-pages-artifact@v3`
+ `deploy-pages@v4`, no `gh` CLI) with the build chain inserted ahead of it, on every push to
`main`:

`actions/setup-node@v4` (Node 26) → `Install seite` pinned via `VERSION=v0.20.1` with
`$HOME/.local/bin` appended to `$GITHUB_PATH` → version assertion → `npm ci` →
`npm run build` → `git diff --exit-code -- static/` (the committed artifacts must be exactly
what CI rebuilds) → `scripts/verify.mjs` → `scripts/verify-theme.mjs` →
`scripts/verify-site.mjs` → `seite build --strict` → `seite check --strict` → upload `dist/`.

`seite upgrade --check` is never run in CI: it always exits non-zero because it wants to write
agent scaffolding.

**One-time repository setting:** Settings → Pages → Build and deployment → Source must be
**GitHub Actions**. Without it the deploy job fails, and the setting cannot be committed — it
is changed in the UI or with `POST /repos/ivan112058/barnacle/pages` and
`{"build_type": "workflow"}`.

### Going live

The workflow is committed and the artifacts it publishes are built, but the site itself is not
up yet: Pages has never been enabled for this repository, so
<https://ivan112058.github.io/barnacle/> answers 404. Three steps, once:

1. **Enable Pages** — Settings → Pages → Build and deployment → Source: **GitHub Actions**, or
   `POST /repos/ivan112058/barnacle/pages` with `{"build_type": "workflow"}`. (Pushing the
   workflow file needs a token with the `workflow` scope; a credential without it is rejected
   outright, which is what blocked the automated attempt.)
2. **Push `main`** — the push is what triggers `.github/workflows/deploy.yml`; watch the run and
   wait for the `deploy` job's `github-pages` environment URL to appear.
3. **Prove it** — the gate, with the HTTP half pointed at the deployment:

   ```powershell
   npm run verify:release -- --live
   ```

   It must print `PASS the site is published at https://ivan112058.github.io/barnacle/`, every
   page and asset at 200, the six `static/` files byte-identical over the wire, and both mirrors
   serving the committed bytes. Anything else is a real defect, not a flake: the offline mode of
   the same script is the reference for what the deployed site must look like.

Re-run `npm run verify:release -- --live` after any deploy. The offline mode stays the gate for
pull requests, because it needs no network.

## Consuming the library

v1 does not publish to npm. There are three supported routes, and `npm run verify:release`
checks all three: the URL routes are parsed out of this README and required to point at files
that exist (and, with `--live`, really fetched), and the per-file route is measured in Chrome
against the whole artifact.

### 1. CDN — jsDelivr, from the `main` branch

```html
<link rel="stylesheet" href="https://cdn.jsdelivr.net/gh/ivan112058/barnacle@main/static/barnacle.min.css">
<script src="https://cdn.jsdelivr.net/gh/ivan112058/barnacle@main/static/barnacle.min.js" defer></script>
```

The unminified pair is published at the same paths, for reading and for debugging:

- <https://cdn.jsdelivr.net/gh/ivan112058/barnacle@main/static/barnacle.css>
- <https://cdn.jsdelivr.net/gh/ivan112058/barnacle@main/static/barnacle.js>

`@main` tracks the branch, which is convenient and not reproducible. Pin a commit sha
(`…/gh/ivan112058/barnacle@<sha>/static/…`) for anything that has to stay put. The artifacts are
committed in `static/`, so jsDelivr serves them without a build step and without an npm package.

### 2. Raw download — GitHub raw

The same four files, straight from the repository:

- <https://raw.githubusercontent.com/ivan112058/barnacle/main/static/barnacle.min.css>
- <https://raw.githubusercontent.com/ivan112058/barnacle/main/static/barnacle.min.js>
- <https://raw.githubusercontent.com/ivan112058/barnacle/main/static/barnacle.css>
- <https://raw.githubusercontent.com/ivan112058/barnacle/main/static/barnacle.js>

`raw.githubusercontent.com` serves them as `text/plain`, so download them and serve them
yourself — do not `<link>` a raw URL into a page.

### 3. Per-file — one `<link>` per source file

For a build that wants to bundle the pieces itself (one file per cascade layer block, so a
bundler's tree-shaking or a CSS-modules pipeline can see them separately), reference
`src/css/` directly. **`00-base.css` and `01-theme.css` are mandatory**: the first carries the
`@layer` declaration and the base layer, the second every `--bn-*` token. The order below is
`CSS_MANIFEST` in `scripts/build.mjs` — the same order the artifact is concatenated in, and the
order a per-file setup must keep:

```
src/css/00-base.css        ← mandatory: the @layer declaration
src/css/01-theme.css       ← mandatory: every token
src/css/animations.css
src/css/button.css
src/css/card.css
src/css/badge.css
src/css/alert.css
src/css/form.css
src/css/table.css
src/css/dialog.css
src/css/accordion.css
src/css/progress.css
src/css/spinner.css
src/css/skeleton.css
src/css/dropdown.css
src/css/tabs.css
src/css/taginput.css
src/css/toast.css
src/css/layout.css
src/css/utilities.css
```

```html
<link rel="stylesheet" href="/vendor/barnacle/00-base.css">
<link rel="stylesheet" href="/vendor/barnacle/01-theme.css">
<!-- … the rest, in the order above -->
```

Two things to know about this route. The layer *assignment* (`@layer components { … }` around
each file) lives in `scripts/build.mjs`, not in the sources, so a per-file setup gets the files
unlayered and the cascade falls back to source order — which is why the order above is not
cosmetic. And anything unlayered that you write yourself then wins over these files, exactly as
it wins over the single artifact (ADR-0006).

`npm run verify:release` builds a page from that list and asserts three computed values — body
background, the button's hard shadow and the card's border — against a page that loads the whole
`static/barnacle.css`, in both themes. If the per-file route ever drifts away from the artifact,
that check is the one that catches it.
