一个容器、一个行，加上十二个列类。这就是全部布局词汇，而把它保持得这么小的意义在于：页面不可能需要一条
这个库没想到的规则——`12` 列、一个断点，以及一个你可以一次调好的间隙。

<!-- fence:0 -->

`bn-container` 居中一条可读的列——`max-inline-size` 是 `75rem`，行内内边距 `2rem`，别的什么都没有。
没有背景、没有边框、没有阴影：布局是一套尺寸，不是一副长相。

`bn-row` 把它的子元素变成一个 12 轨的栅格。`bn-col-1` 到 `bn-col-12` 说明一个子元素占其中几条轨道，而
每一行加起来应当是十二。

### 断点

断点恰好只有一个，是 **768px**——和 `48rem` 同宽，因为媒体查询里的 `rem` 是按 16px 的初始字号解析的，
而不是按页面自己的字号。在它之上，一列横跨它的类要求的那些轨道。等于或低于它时，**每一个**列都变成整行
宽度，不论它带的是哪个类：在手机上，一个三列卡片栅格变成一个单列列表，不需要第二个类名，页面里也不需要
媒体查询。

这唯一的断点是刻意的边界，不是疏忽。一套响应式列语言（`bn-col-md-6`、`bn-col-lg-4`……）会把十二个类乘以
断点数量，而工具集应当小到一屏就能读完。一个确实需要另一种节奏的页面有两个不花库一分钱的选择：自己写媒体
查询——不分层的 CSS 赢过每一个层（ADR-0006）——或者去用工具类页上那四种固定组合。

栅格是从最窄的视口往上逐个检查的，所以「会坍缩」是一个被测过的说法而不是一个意图：**320、375、768、1024
与 1440** 像素，在真实 Chrome 里，断言 `document.documentElement.scrollWidth` 从不超过视口宽度，并且
每行的列数就是类所要求的。在 768px 以下，本页每个示例都是一列宽；前面那两个示例在手机上一列，从 768px 起
是严格的三分之二 / 三分之一。

### 为什么用栅格，以及每列一个自定义属性

列是用 CSS grid 排的，而每个列类只携带 `--_span: n`。家族规则把这个数字读一次：

<!-- fence:1 -->

另一条路是 flex 行，让每一列带一个百分比宽度。栅格在三点上胜出，而这三点在文档站和在应用里一样要紧：
间隙就是一个 `gap`，所以没有哪一列需要从百分比里减去自己那份间隙，行与行之间也不会漂出几分之一像素；一列
可以被压到比它的内容还窄（`minmax(0, 1fr)` 加上 `min-inline-size: 0`），而这正是一个长的、无法断行的
令牌所需要的；整套响应式行为是一个媒体查询，只碰到一处声明，而不是再多十二条规则。

有一个后果值得知道，因为它是继承来的、而不是显而易见的。`--_span` 会层叠，所以嵌在某一列里的 `.bn-row`
会继承父元素的 span，把自己的子元素铺在父列的那些轨道上。行会把它重置：嵌套的行永远从干净的十二列开始。

### 间隙与硬阴影

`--_grid-gap` 默认是 `1.5rem`（24px），这个数字不是随便取的：库里最大的硬阴影偏移是 `--bn-shadow-lg`，
在默认的 4px 基准下是 6px。比这更窄的间隙会让一张卡片的阴影落到邻居身上，那读起来像渲染错误而不是样式。
如果你为了更密的布局收紧间隙，要么把间隙抬回阴影偏移之上，要么在 `:root` 上用库的阴影令牌把那几张卡片
降到更小的一档。
